Yes. I think your reasoning changes the direction of the project in an important way.

The **systematic goal should be: upscale essentially every texture that is actually visible to the player, with category-specific handling where the texture's semantics require it.** We don't need to build an elaborate exclusion system just because some categories are unusual.

There are, however, a few things I would keep separate.

## 1. Player colour: I agree with your proposed universal rule

The important discovery is that the player-colour information lives in the **alpha channel**, not in the RGB artwork itself.

AoM documentation explicitly describes unit texture alpha as being used to determine player-colour/transparency regions, and the File Converter documentation says `noalphatest` is typically used when alpha represents where player colour is applied. ([SteamSolo][1])

So if our building experiment demonstrated:

**RGB → AI 4× upscale**

**Alpha → nearest-neighbour 4× upscale**

then reconstructing:

**AI RGB + NN Alpha → TGA**

is preserving the important runtime information while improving the visible artwork.

### I therefore agree with making this the default pipeline.

Rather than:

> "Find all player-colour textures and treat them specially."

we can potentially make the much simpler rule:

> **For every 32-bit texture, upscale RGB with the selected AI model and upscale alpha independently with nearest neighbour.**

That is actually much safer.

It means we don't have to perfectly identify the 948 `noalphatest` textures or the 134 candidates before proceeding.

The alpha channel is preserved **regardless of whether we understand its semantic purpose**.

### One important caveat

I don't want to blindly assume that *every* alpha channel should be nearest-neighbour.

There are at least three fundamentally different possibilities:

1. **Binary mask / player-colour mask**
   → nearest neighbour is exactly what we want.

2. **Normal transparency with smooth gradients**
   → nearest neighbour could produce unnecessarily hard/stepped edges.

3. **Special-purpose alpha data**
   → requires investigation.

So the eventual automated pipeline should probably inspect the alpha channel and select the treatment accordingly.

But we can initially test the simplest universal rule:

> **AI RGB + NN alpha**

on a large representative sample.

If it works visually across buildings, units, animals, effects and UI, we have an extremely elegant solution.

# 3. Shadows: I think your proposed approach is probably correct

I would currently classify shadows as:

> **Do not upscale unless investigation demonstrates that the texture is actually a player-visible shadow asset whose resolution materially affects the rendered result.**

The important distinction is between:

### A. Runtime-generated shadows

The engine calculates the shadow from geometry/light/shadow settings.

Upscaling a texture does nothing for that.

### B. Shadow-related textures

For example:

* baked shadow/decal textures;
* soft shadow masks;
* special unit shadow assets;
* texture-based effects;
* Hades-specific artwork that happens to be classified as a shadow.

Those **could** benefit from upscaling.

And I agree with your concern about something like the **Hades Shadow** unit.

We don't want:

> "Skip the Shadow category"

to accidentally mean:

> "Delete/ignore everything whose filename or inventory classification contains Shadow."

Instead:

### New proposed rule

**Investigate the 436 Shadow-classified textures individually/by family.**

Determine whether each one is:

* runtime shadow data,
* an actual visible texture,
* a unit/creature texture,
* a decal,
* an effect,
* or some other asset.

Then exclude genuine engine-generated shadow resources from the AI pipeline.

That should be relatively straightforward once we correlate filenames/materials/models.

The game's shadow quality is independently controlled by engine settings and has historically been a significant rendering-performance setting, which is consistent with shadows being at least partly generated by the renderer rather than simply being texture-resolution dependent. ([Steam Community][3])

So I would **not touch the normal shadow system** for this project.

# 4. UI is the area where we need more testing

This is where I would *not* immediately assume:

> 4× texture = 4× physical UI size.

Textures and UI layout are different things.

Suppose the game has:

```text
Button texture: 128 × 64
```

and the UI code displays it at:

```text
128 × 64 screen/UI units
```

Replacing the texture with:

```text
512 × 256
```

doesn't necessarily make the button four times larger.

It may simply give the same button more pixels to render.

**That's exactly what we want for a high-resolution remaster.**

However, we need to test how AoM EE's UI system handles:

* fixed-size UI elements;
* stretched textures;
* nine-slice-like elements, if any;
* tiled textures;
* resolution scaling;
* aspect ratios;
* texture coordinates;
* text;
* icons embedded inside larger UI textures.

So I would make **UI testing a dedicated stage**, not an afterthought.

# 11. I mostly agree with your VRAM argument, with one qualification

Your starting point is sound.

If the unmodified game is only using roughly **0.2–0.7 GB VRAM in your testing**, then there is enormous headroom on modern GPUs.

But texture VRAM usage doesn't scale simply as:

> 4× resolution = 4× VRAM.

For a 2D texture:

**width ×4 × height ×4 = 16× as many texels.**

So an individual 256×256 texture becomes:

**1024×1024**

with **16× the texel count**.

And thousands of textures can accumulate.

Compression, mipmaps, streaming, texture reuse and actual residency complicate the real number considerably.

Therefore I would say:

> **4× is very likely viable for modern PCs, but we should verify it rather than guarantee it.**

And fortunately, this is an easy test.

We can make the complete 4× texture pack and test:

* 1080p
* 1440p
* 4K
* large battles
* multiple civilizations
* large maps
* campaign scenarios
* menus
* god powers/effects

while monitoring VRAM.

Given your hardware targets, I expect performance to be much less concerning than **whether the old engine handles the enlarged assets correctly**.
